# ADR-002 — Data Persistence Strategy

**Status:** Accepted
**Date:** 2026-06-16
**Author:** Yomal
**Project:** BISTEC PMO Ticket Triage Dashboard

---

## Context

The Ticket Triage Dashboard needs to store ticket data somewhere. This is OQ-02 from the PRD. The key constraints are:

- v1 has **no backend** and **no user authentication** (explicitly out of scope).
- Amara enters 20–50 tickets per day — losing them on a page refresh is unacceptable.
- Dinesh needs to see the same ticket state as Amara — shared access is required.
- The dashboard must support up to **500 tickets** without degradation (NFR-04).
- The dashboard is used during **BISTEC working hours only** (NFR-03), on **office machines**.

Three options were considered:

### Option A — In-memory state only (React useState)
All ticket data lives in React state. Refreshing the page wipes everything.

**Pros:**
- Zero setup. No storage layer at all.
- Simplest possible implementation.

**Cons:**
- A page refresh loses all tickets — completely unacceptable for a real PMO tool.
- Cannot be shared between Amara's and Dinesh's browsers.
- Violates G4 (no critical ticket missed) the moment someone accidentally refreshes.

**Verdict:** Eliminated. Data loss on refresh is a hard blocker.

---

### Option B — Browser localStorage
Tickets are serialised to JSON and written to `localStorage` on every change. On load, the app reads from `localStorage` to restore state.

**Pros:**
- No backend required — stays within the v1 "no server" constraint.
- Survives page refresh.
- Simple to implement: `JSON.stringify` / `JSON.parse` with a single key.
- 500 tickets at ~500 bytes each = ~250 KB — well within the 5 MB localStorage limit.

**Cons:**
- **Data is per-browser, per-device.** Amara's tickets are not visible to Dinesh unless they use the same machine or same browser profile.
- No real-time sync between two users.
- Data is lost if the user clears browser storage.

**Verdict:** Viable only if both users share a single machine or browser profile. Not suitable for a multi-user PMO team.

---

### Option C — Lightweight backend with a REST API + persistent database
A Go or Node.js API server with a SQLite or PostgreSQL database. React frontend calls the API to read and write tickets.

**Pros:**
- Tickets are shared across all users and devices.
- Data is durable — survives refreshes, machine changes, and browser clears.
- Naturally supports 500+ tickets with proper querying.
- Sets up the foundation for v2 features (auth, Jira integration, analytics).

**Cons:**
- Requires a server to run and a database to provision.
- More setup and deployment complexity than a pure frontend.
- Technically out of scope for a v1 spec-first challenge — but not unreasonable for a real PMO tool.

**Verdict:** The right long-term answer, but adds deployment scope to a v1 challenge build.

---

### Option D — JSON file served locally / JSON Server (mock backend)
Use `json-server` — an npm package that spins up a REST API from a flat `db.json` file. The React app calls it just like a real API.

**Pros:**
- Tickets persist in `db.json` on disk — survives refresh.
- Full REST semantics (GET, POST, PATCH, DELETE) with zero backend code.
- React data-fetching layer is written the same way it would be against a real API — making v2 migration trivial.
- Shared access: both users can hit the same `json-server` instance if it runs on one machine on the local network.
- No database provisioning required.

**Cons:**
- Requires Node.js on the machine running the server.
- `db.json` is not a real database — no transactions, no concurrency safety.
- Not suitable for production, but entirely appropriate for v1 / a spec-first challenge deliverable.

---

## Decision

**Option D — `json-server` as a local mock backend** is selected for v1.

`localStorage` (Option B) fails the multi-user requirement — Amara and Dinesh are on separate machines. A full backend (Option C) is the correct long-term answer but exceeds v1 scope. `json-server` (Option D) hits the sweet spot: tickets persist in a file, both users can share the data on a local network, and the React data-fetching code is written against real REST endpoints — meaning the migration to a real API in v2 is a config-level change, not a rewrite.

In-memory only (Option A) is eliminated immediately due to data loss on refresh.

---

## Consequences

**Positive:**
- Tickets survive page refreshes and browser restarts.
- Amara and Dinesh share the same ticket state during working hours if `json-server` runs on one office machine.
- React's data layer (`fetch` / `axios`) is written against real REST endpoints — v2 backend swap requires only a base URL change.
- `db.json` can be committed to the repo as a seed file with sample tickets for demos and testing.

**Negative / trade-offs:**
- Someone must keep the `json-server` process running during working hours.
- No auth — anyone on the same network can read/write tickets. Acceptable for v1 (no auth is explicitly out of scope in the PRD).
- Concurrent writes from two browsers simultaneously are not safe — `json-server` has no transaction support. Acceptable at PMO scale (one active triager at a time).

**Migration path to v2:**
When v2 adds a real backend (Go + PostgreSQL is the natural BISTEC choice), the React frontend changes only the `API_BASE_URL` constant. All `fetch` calls stay identical.

**Follow-on decisions required:**
- Deployment: where does `json-server` run — one designated office machine, or a lightweight Azure VM? This is a v2 decision; for v1 it runs on the developer's local machine.
