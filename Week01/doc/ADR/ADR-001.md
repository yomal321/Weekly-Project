# ADR-001 — Frontend Framework Selection

**Status:** Accepted
**Date:** 2026-06-16
**Author:** Yomal
**Project:** BISTEC PMO Ticket Triage Dashboard

---

## Context

The Ticket Triage Dashboard is a single-page web application used by non-technical PMO staff (Amara and Dinesh) on office laptops running Chrome or Edge. It needs to:

- Render a live-sorted ticket list that re-orders immediately after priority changes (FR-03, FR-06).
- Handle filter state changes without a page reload (FR-07).
- Stay simple enough to build and maintain by a single developer (intern level).
- Require no backend — v1 is a frontend-only app (out of scope: no auth, no integration).

Three options were considered:

### Option A — Plain HTML + Vanilla JavaScript
No build tooling, no dependencies. Write DOM manipulation directly.

**Pros:**
- Zero setup time.
- No build step — just open `index.html`.
- No framework churn.

**Cons:**
- Manual DOM diffing and list re-sorting gets messy fast as ticket state grows.
- No component model — ticket card markup gets duplicated or stringified.
- TypeScript support requires extra setup.
- Hard to maintain beyond ~200 lines.

---

### Option B — React + TypeScript (Vite)
Industry-standard SPA framework with a lightweight build setup via Vite.

**Pros:**
- Component model maps cleanly to the ticket card and dashboard layout.
- State-driven re-render means sorting and filtering are automatic — just update state.
- TypeScript first-class — catches priority/status type errors at compile time.
- Vite starts in < 1 second; hot reload makes iteration fast.
- Aligns with BISTEC's existing TypeScript stack.
- Large ecosystem: easy to add Tailwind, shadcn/ui, or Lucide icons.

**Cons:**
- Requires Node.js and a build step.
- Slightly more setup than plain HTML.
- Overkill for a truly trivial app — but this one isn't trivial (live sorting, filter state, form).

---

### Option C — Vue 3 + TypeScript (Vite)
Alternative SPA framework with a similar build profile to React.

**Pros:**
- Gentler learning curve than React for some developers.
- Options API is readable for non-React developers.

**Cons:**
- Not part of BISTEC's existing stack.
- Smaller ecosystem footprint compared to React.
- No meaningful advantage over React for this use case.

---

## Decision

**Option B — React + TypeScript (Vite)** is selected.

The dashboard has real reactive state: a ticket list that re-sorts on priority change, filter state that controls which tickets render, and a form that adds new tickets. React's component + state model handles all three naturally. TypeScript adds the type safety needed for the `Priority` and `Status` enums that drive the sort and filter logic. Vite keeps the dev setup lightweight. Option A becomes unmaintainable once the DOM manipulation grows; Option C adds no advantage while diverging from the BISTEC stack.

---

## Consequences

**Positive:**
- Ticket sort and filter logic lives entirely in state — no manual DOM manipulation.
- `Priority` and `TicketStatus` can be TypeScript enums, preventing invalid values from reaching the UI.
- Component structure maps directly to the PRD: `<Dashboard>`, `<TicketList>`, `<TicketCard>`, `<AddTicketForm>`, `<FilterBar>`.
- Consistent with the TypeScript skills Yomal is developing at BISTEC.

**Negative / trade-offs:**
- Requires Node.js and `npm install` to run locally — not a simple file-open.
- Bundle size is slightly larger than a vanilla JS file, but negligible for an internal office tool.

**Follow-on decisions required:**
- ADR-002 will decide where ticket data persists (impacts React state management approach).
- A UI library choice (Tailwind CSS) should be made before implementation starts, but does not require a separate ADR at v1 scope.
